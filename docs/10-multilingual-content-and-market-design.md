# 多语言商品内容与国家市场设计

版本：`v0.1-draft`  
需求确认日期：`2026-11-03`  
状态：已确认“自动切换并忠实复刻 Joybuy 混合语言内容”，尚未开始业务代码改造

## 1. 用户目标

- 后续 Joybuy 来源分析优先使用简体中文页面；
- 系统自动为不同国家/地区和语言保存 Joybuy 实际返回的内容版本，不要求用户点击“翻译”；
- 用户切换国家/语言后，导航、类目、列表、商品标题、介绍、属性、活动和评价等内容一次性自动刷新；
- Joybuy 德国页面中实际为德文的字段显示德文，实际仍为英文的字段保留英文，允许同一页面出现德英混合；
- 默认目标是忠实复刻 Joybuy，而不是把所有字段强制机器翻译成单一语言；
- 每个字段必须记录请求市场、请求语言、实际内容语言和来源，不能把英文回退误标为德文。

## 2. 已完成的现场设置

2026-11-03 已在 Joybuy 公开页面的“Custom settings”中选择并保存 `中文(简体) - ZH`，页面标题变为“Joybuy | 一站式购物平台”，导航、活动入口与商品标题均已显示中文。

该中文浏览器会话已保留，后续类目分析必须从此中文页面重新开始。此前英文页面分析只作为历史参考，不能直接生成最终中文类目数据。

当前英国区域设置下，页面公开的语言选项为英文和简体中文。本轮没有继续切换其他国家或分析类目。

## 3. 必须拆开的三个维度

### 3.1 来源语言 `source_locale`

表示爬虫本次读取 Joybuy 页面时使用的语言，例如 `zh-CN`。所有进入 staging 的文本都必须携带来源语言，不能靠内容猜测。

### 3.2 请求语言 `requested_locale`

表示用户在 Joybuy/本地站点选择的语言环境，例如：

- 简体中文：`zh-CN`
- 英国英语：`en-GB`
- 德国德语：`de-DE`

同一 `requested_locale=de-DE` 页面中的不同字段仍可能分别是德文或英文，所以每个文本字段还要记录 `actual_locale`。

### 3.3 国家市场 `market`

决定商品是否可售、价格、币种、税费、库存、配送范围和时区，例如：

- 英国市场：`GB`、默认 `en-GB`、`GBP`；
- 德国市场：`DE`、默认 `de-DE`、`EUR`。

国家与请求语言默认联动，但数据模型必须分开。用户选择德国市场时，系统自动使用 Joybuy 对德国市场给出的默认语言、欧元和配送规则；后续是否允许在德国市场手动选择其他语言，以 Joybuy 当时页面实际选项为准，不自行扩展。

## 4. 哪些内容需要多语言

| 内容 | 处理方式 |
| --- | --- |
| 商品标题、副标题、卖点、详情介绍 | 按 `market + requested_locale` 保存 Joybuy 实际返回的版本，并逐字段记录 `actual_locale` |
| 来源类目、本地类目、商品类型 | 来源类目按市场/请求语言保存 Joybuy 原文；本地运营类目另建 locale 内容 |
| 属性名、规格名、规格选项 | 保存 Joybuy 当前页面实际文本；型号、容量数值保持原样 |
| 活动标签、促销文案 | 按市场和请求语言保存 Joybuy 实际内容，价格数字来自对应 Offer |
| CMS 标题、横幅、专题文案 | 来源专题忠实保存 Joybuy 版本；本地 CMS 按 locale 建内容版本 |
| 品牌名、型号、GTIN/EAN | 默认保持原文，不自动意译 |
| 单位、日期、数字、货币 | 使用 locale 格式化；价格值来自市场 Offer，不通过汇率临时换算 |
| 用户评价 | 按当前市场/语言页面自动显示 Joybuy 实际提供的文本；不提供用户触发的翻译按钮 |
| 图片中的文字 | 首期不自动改图；必要时由本地化素材版本解决 |
| 法规、安全警示、成分与过敏原 | 忠实保存 Joybuy 当前市场页面内容，不自行补译、改写或补全 |

## 5. 推荐的多市场本地化采集流水线

```text
用户切换国家/语言
  -> 前端同时更新 market + requested_locale
  -> 所有 API 使用新的请求上下文重新加载
  -> 读取对应 Joybuy 市场/语言快照
  -> 逐字段返回 Joybuy 实际内容（可德英混合）
  -> 返回价格、币种、库存和配送的对应市场数据
  -> 为 market + requested_locale 重建/读取搜索索引
```

来源采集也按同一结构运行：爬虫分别进入 Joybuy 实际支持的市场/语言组合，保存页面原样内容。第一批建议验证英国中文、英国英文和德国默认语言；德国页面具体德英混合规则要在后续现场分析中记录，而不是预先假设所有文本都应为德文。

机器翻译不属于默认复刻链路。若未来要增加“本地增强翻译”，必须作为与 Joybuy 来源内容分离的本地覆盖功能另行立项，不能替换默认来源版本。

## 6. 本地化来源状态与字段追溯

每一份本地化内容至少记录：

- `market`
- `requested_locale`
- `actual_locale`（逐字段记录，可为空表示无法可靠识别）
- `origin`：默认 `SOURCE`；未来本地覆盖才使用 `MACHINE` / `HUMAN`
- `source_content_hash`
- `status`：`CURRENT` / `STALE` / `FAILED`
- 来源 URL、抓取时间、解析器版本和来源树版本

Joybuy 原文变化后：

1. 保存新的来源值与哈希；
2. 旧来源版本保留用于审计；
3. 对比同一市场/请求语言中的字段变化；
4. 已人工覆盖的本地内容不能被来源刷新直接覆盖；
5. 重建对应市场/请求语言的展示与搜索索引。

## 7. 展示与回退规则

### 7.1 购物端

用户只负责选择 Joybuy 已公开的国家/语言，不负责触发翻译。切换后系统自动刷新全部页面数据：

- 德国 Joybuy 页面返回德文标题、英文详情时，本地也显示“德文标题 + 英文详情”；
- Joybuy 返回英文商品名时，不强制改成德文，也不隐藏商品；
- 不显示“点击翻译”按钮，不等待用户操作；
- 不把 `requested_locale=de-DE` 等同于“每个字段实际都是德文”；
- 页面固定 UI 文案、商品内容、类目、CMS 和搜索结果必须在同一次切换中一起更新。

### 7.2 平台管理端

管理员可以查看所有 locale，并看到：

- Joybuy 原文；
- 当前市场/请求语言的 Joybuy 来源值；
- 每个字段实际检测或确认的语言；
- 人工覆盖值；
- 翻译状态和最后同步时间；
- 原文变化与待复审提示。

管理端应能并排比较英国中文、英国英文、德国默认语言等来源快照，便于确认混合语言是否来自 Joybuy，而不是系统错误。

## 8. 对现有数据模型的影响

### 8.1 可以复用的部分

- 现有 `SpuTranslation(spu, locale, title, subtitle, description)` 具备一件商品多语言的雏形，但不能表达市场差异和单字段混合语言；
- 现有 `Market.default_locale` 与 `Market.default_currency` 可继续使用；
- 现有来源层、人工覆盖层和版本审计机制可以扩展到每个 locale 的翻译对象。

### 8.2 必须补齐的部分

- 将商品来源内容扩展为对 `(spu, market, requested_locale)` 唯一，或新增等价的市场本地化内容模型；
- 为每个文本字段保存 `actual_locale`、来源哈希和观察时间；
- 增加 `Locale` 与 `MarketLocale`，只暴露 Joybuy 当前实际支持的市场/语言组合；
- 增加类目、属性、属性选项和 CMS 的翻译表；
- staging 载荷必须保存 `market`、`requested_locale` 和字段语言元数据，不能继续依赖调用方默认值；
- 商品详情 API 不能再取“第一条 translation”，必须按市场和请求语言精确解析；
- 搜索 API 不能继续固定 `GB` 市场。

### 8.3 搜索索引必须重构

现有 `ProductSearchDocument` 是每个 SPU 仅一行，且只有一个标题，无法支持多市场多语言。应改为对 `(spu, market, requested_locale)` 唯一：

- 使用 Joybuy 在该市场/请求语言页面实际返回的标题与描述建立索引，即使其中混合英文和德文；
- 中文搜索需要 MySQL `ngram` 全文解析器或经过验证的分词搜索列，不能直接照搬英文 FULLTEXT 行为；
- 对应市场/请求语言的来源快照通过质量闸门后即可建立索引，不要求所有字段属于同一种语言；
- 价格、币种、可售状态来自对应 market 的 Offer。

## 9. 请求与前端解析

建议请求上下文同时携带：

- `market`：Cookie 或路由上下文，例如 `DE`；
- `requested_locale`：Cookie、路由前缀或 `Accept-Language`，例如 `de-DE`；
- `currency`：默认跟随 market，仅在该市场允许时单独切换。

API 必须回传最终使用的 `market`、`requested_locale`，必要时返回字段级 `actual_locale`，避免前端把英文来源误判为回退错误。

购物端界面固定文案使用本地 i18n 资源文件；商品内容来自后端 locale 表。两者是两套内容来源，必须同时切换。

## 10. 来源忠实度质量规则

- 品牌、型号、SKU、容量、单位和原始文本不得由默认复刻链路改写；
- HTML 详情结构化保存，不改变标签层级和文本顺序；
- 保留列表、段落、表格和强调结构；
- 数字、货币、尺寸和温度做结构校验；
- 禁止自动补写或翻译来源不存在的功效、认证、材质或参数；
- 语言检测只用于记录 `actual_locale` 和发现异常，不用于把英文内容自动改成德文；
- 同一页面的德英混合是允许状态，只要与 Joybuy 来源一致；
- 若本地内容与来源快照不一致，暂停该市场/语言批次并保留原始响应重放。

## 11. 与爬虫品类方案的关系

后续中文类目分析按以下顺序进行：

1. 使用已经保存的 Joybuy 简体中文会话；
2. 保存中文来源名称、稳定公开标识和树版本；
3. 中文名称作为英国中文设置下的来源内容，不再由英文类目临时翻译；
4. 后续分别切换到目标国家/语言，保存 Joybuy 实际返回的类目名称，不做强制机器翻译；
5. 德国页面出现德英混合时逐字段原样保存；
6. 业务分组和配额仍使用 [爬虫任务品类与配额页面改造方案](./09-crawler-category-task-redesign.md) 的设计；
7. 各目标市场/语言现场分析完成前不生成最终 seed fixture。
